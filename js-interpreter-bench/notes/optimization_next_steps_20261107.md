# Octane 优化下一步：从净收益推进到可归因的执行路径改进

计划依据本机 `experiments/native_octane_20261107/attempt01/` 的680条新性能样本及历史机制实验提出。提出时尚未实现或采集新的优化版本，后续进展单列如下。

后续进展：用户已授权验证P1+B2，且要求复用旧对照。组合完成85条新Octane样本，核心相对旧A耗时-4.37%、相对旧P1为-1.72%；扩展集合分别-4.36%、-1.49%。两条机制均实测命中，统计独立复算通过；属于跨批次探索，LSan在当前环境不可用。详见[组合结果](../experiments/native_octane_20261107/attempt02/summary.md)。下文保留提出计划时的依据和未验证预算模型。

第二次进展：下述两项改动已分别基于冻结P1+B2实现，并完成各五轮Octane（合计170条新性能样本）。PREP2合并准备扫描，核心相对父版-0.44%、相对A-4.79%，增量95%探索区间[-0.89%, +0.13%]跨零；SPLIT16区分记录布局，核心相对父版+0.77%、相对A-3.64%。未组合、未追加轮数，旧对照未重跑。两版专项安全、34条Octane正确性、原始数据审计和统计独立复算通过；LSan关闭。PREP2只保留为小幅候选，布局版保留负结果。详见[两项改动结果](../experiments/native_octane_20261108/attempt01/summary.md)。下一步优先做冻结父版的成本归因，而非继续无依据地组合布局或加载形式。

第三次进展：用户授权验证准备分配、选择性融合和调用清理三个方向。独立父版N=1计数及Callgrind诊断后，分别基于PREP2实现COALLOC（源码编译时合并最终分配）、FUSE_A1L1（只增加arg1/loc1）、CALL02（0～2参数返回后清理展开）。三个新版本共255条五轮Octane、51条正确性及专项安全检查完成，审计/独立复算通过。核心相对PREP2为+1.26%/+0.26%/+0.71%，相对A为-3.59%/-4.54%/-4.11%；FUSE区间跨零，未晋级、未组合或追加轮数。后补独立N=1指令诊断确认FUSE/Boyer总Ir降低1.32%、CALL02/Richards降低0.80%，后者原生时间却增加12.53%；不能把指令减少等同周期收益，具体布局/分支/缓存贡献仍未知。attempt02因新增测试API签名错误在编译时停止且无性能点，失败保留；修正后的完整批次为[attempt03](../experiments/native_octane_20261108/attempt03/summary.md)。继续保留旧PREP2点估计及P1+B2参考。

第四次进展：继续实际实现CHAIN2（由参数/局部槽保活根对象的连续两次own读借用融合）与READ_STORE（写入复用同atom前置读点，不增加写记录）。两版170条五轮Octane及34条正确性、安全/ASan/UBSan/热roundtrip/native finalizer、独立统计复算完成。核心相对PREP2为-0.08%/-0.24%，区间跨零；相对A为-4.87%/-5.02%，扩展为-4.88%/-4.96%。两版Mandreel分别降低2.32%/3.69%，但后补同输入N=1 Run覆盖均为0查询/0命中；仅作诊断排除它后，其余核心聚合反而为+0.107%/+0.054%。不能将5.02%点估计称为已确认超过5%或预期机制的稳定增量。新原生指令数据：CHAIN2/Richards总Ir-1.03%、原生时间-1.19%；READ_STORE/Richards总Ir+0.57%、时间+1.37%。未组合、未追加轮数，保留候选材料。详见[attempt04](../experiments/native_octane_20261108/attempt04/summary.md)。

**用户确认的后续采样策略**

探索阶段每个benchmark/新版本先采5个独立新进程，保持进程内既定N与原输入；复用近期冻结对照以节约时间，明确标注跨批次比较。不给所有中间候选追加多轮，也不因结果接近阈值就反复补样本。小幅或方向不一致的信号保留为不明确。等较好的最终方案确定后，再预先固定确认轮数，以新同批交错的A/父版/候选完成多轮验证；最终确认不能以反复追加到显著为停止规则。

本次P1+B2五次数据的逐项CV（样本标准差/均值）中位数0.47%，17项中14项低于1%，最大为JQuery的1.72%；其次RayTrace约1.35%、Mandreel约1.26%。按每轮单独聚合、对照旧A中位数，核心改善依次为3.90%、4.32%、4.44%、4.11%、4.19%，跨度约0.54个百分点。最终4.37%的口径是先逐项取五次中位数再聚合，不是这五个整轮分数的中位数。上述随机波动不覆盖复用旧对照的系统漂移。

**组合后的优先改进建议（提出时尚未实现，现有结果见后续进展）**

以冻结P1+B2为新候选父版，优先回收准备与元数据开销。现有CodeLoad.Closure/JQuery相对A为+10.09%/+6.37%，Splay为+3.82%。仅作预算模型、假设其余条目不变：CodeLoad两子项都恢复A耗时后核心改善约4.95%；再使Splay恢复A后约5.23%。这不是测得的优化机会，也不允许按benchmark名字禁用IC。

两个可分别验证的改动：

- 合并准备遍历：当前有字段读取的函数在rdi_prepare中依次经历计数、改写读opcode、标记B2融合三次扫描。标记相邻arg0/loc0+原get_field可尝试并入改写扫描，保留两条指令长度、独立入口及同样的准入结果。先证明最终执行字节码与缓存记录映射等价；只减少遍历，不增加运行期准入分支。CodeLoad在Run内动态编译，使这部分工作可能进入计时，但占比尚未测出。
- 区分记录布局：P1新增holder_shape，使普通get_field和get_field2记录全部从16B变成24B。可尝试普通读保留16B，get_field2使用带holder的24B记录；保持单块分配及PC相对直接定位，避免普通命中额外追侧表。GC、释放、普通/原型状态转换和序列化要按两类记录同步调整。这仅减少普通读记录的三分之一空间，不意味着整体内存或时间减少三分之一。旧v5的epoch原型侧表、v7的多态AP1不是这一布局方案。

两版先分别基于原组合测试，每项五个新进程，沿用近期冻结对照、标注跨批次；有独立净收益才考虑组合。若需要进一步扩大B2覆盖，先诊断哪些尚未融合的加载组合真实高频，再限定增加少量形式；旧d04已经尝试过全部八种准备后加载融合，不应原样重复并称新方向。旧L1/AQ1也已有结果，不以无依据的热度阈值搜索替代成本核查。

**当前结论与目标预算**

- 本机最佳P1：核心16项/13suite相对A耗时-2.70%，扩展17项/14suite为-2.92%。P1可以保留为候选，不据这次Octane结果替换全部平台的默认底座。
- P1/V8_ON核心耗时比1.661664；要使该比值达到1，P1仍需减少约39.82%的耗时。因此“超过5%”和“接近V8”是两个不同规模的目标。
- 各候选共同包含s001。P1/A=0.972996，B2/A=0.976580，s001/A=0.990022，不能直接相加它们对A的收益。仅作预算示例：若二者在s001上的增量完全独立，组合/A为P1×B2/s001≈0.959785，即-4.02%。这是未验证的独立性模型，不是组合性能预测或收益上限。
- 查询/命中次数不能替代耗时占比；旧read_ic_mic、ic_mechanism_audit已经验证命中省查找，也保留了高命中而整体不快的反例。旧call_boundary_cost的调用时间归因未通过扰动门禁，不能倒填成调用已被证实是热点。

**推荐执行顺序**

1. 小成本核对一版P1+B2组合，只验证互补路径是否能叠加。先恢复对应冻结源码并做差异/语义检查，所有比较版本用同一工具链；以A、s001、P1、B2及组合为对照。若组合在代表案例没有可靠增量，停止组合搜索；有信号才进入新的完整Octane批次。组合若失败不拆成大量参数变体继续搜。
2. 主线优先对EarleyBoyer、RayTrace、CodeLoad做A/P1诊断，Richards作已知局部收益对照。保留原程序、原Run边界，计时区间外的加载/必需Setup不混入归因。先得到每case的热点图、关键调用链及可解释的动态指令/分配/引用操作工作量，再选择一个改动。
3. 当前perf实际检查失败，perf_event_paranoid=4，硬件/软件事件访问受限；未修改系统设置。Callgrind已安装且工具可启动，可先作受控诊断；其指令数、调用和模拟缓存结果不是原生耗时占比。若使用既有信号采样框架，先核对实际间隔与扰动，不复用旧WSL的失败时间归因。
4. 优先验证跨多个suite的成本假设：临时receiver/参数的重复Dup/Free、普通JS调用进入退出、重复栈搬运与相邻opcode支撑工作。已有B2/C1只省去某些加载/分发，不能把它们当成调用/引用管理成本已经解决。改动必须保持异常、getter/Proxy、重入、GC及保存加载语义；安全的普通路径之外保留通用处理。
5. CodeLoad作为回归约束：P1的Closure/JQuery分别比A慢7.21%/3.49%，B2为10.51%/6.24%。旧lazy/布局/多态版本已有负结果，下一轮应先定位准备和维护的实际成本，而不是再次宣称这些思路尚未尝试。
6. 有明确增量后才做完整17项新批次，以固定P1和A为同批基准、V8_ON为参照；不运行V8_OFF，不变更benchmark算法。全部正负结果、内存代价及失败保留。编译器/LTO/PGO实验若另做，单列为构建控制，不记成IC算法收益。

**RegExp作为单独工程路线**

如果目标是完整Octane分数，应保留RegExp专题；如果目标是解释器/IC研究，其结果也应与JS执行路径改进分别说明。按核心13suite等权定义，假如整个RegExp条目耗时减半且其它suite完全不变，核心GM耗时会下降约5.19%。这只说明预算权重，并不证明正则引擎已存在可实现的2倍机会。

V8的`--jitless`仍使用Ignition执行用户JS，正则匹配也由解释器执行，同时保留预先编译的native builtins；不能把全部差距称为IC差距，或解释为偷偷启用JS JIT。该原则见[V8官方jitless说明](https://v8.dev/blog/jitless)，具体15.6.21运行路径仍须靠当前制品诊断确认。

QuickJS的引用计数和值生命周期规则见[官方手册](https://bellard.org/quickjs/quickjs.html)。Ignition的寄存器/累加器与预生成handler设计见[官方说明](https://v8.dev/blog/ignition-interpreter)；这些架构差异是待检验的研究线索，不是现在就重写寄存器VM的证据。Callgrind的采集控制和数据含义见[官方手册](https://valgrind.org/docs/manual/cl-manual.html)。

下一轮最重要的产物应是：一个在原生环境中可复核的成本假设、一处边界明确的实现，以及跨多个Octane条目的同批净收益。当前证据不足以承诺超过5%，更不足以承诺通过属性IC调参取得接近40%的整体耗时下降。
