## 做了什么

尝试六类思路，共12个结构原型。前11个完成完整17项 Octane 单次筛选，每个候选都与新 s001 进程交错。d05 通过构建与正确性后计时受阻。另保留两个宏声明顺序导致的构建失败版本，以及两个在采样前因引用释放顺序审阅撤回的共享动作版本。

每个可运行版本均通过4组 JS 门禁，输出分别为7020、9013、1941、6019条断言。这些数字反映断言次数。覆盖换值、不同布局、删除/重定义、getter、Proxy、原型变化等，完整 test262、ASan/UBSan、最终 GC/OOM/qjsc 验收本轮尚未执行。

主指标为内部原生单调计时的完整 Run 耗时，包含首次调用，计时前没有 workload 预跑。GC、helper、builtin、RegExp 和 workload 内动态编译按实际行为计入。初筛使用既有 N 的四分之一，Crypto 保持确定性完整 N。独立复测使用完整 N，所有条件共同使用同 case 的 N。

## 目前解释到哪一步

d03 的变化在短参数/局部变量加载 handler。若后一条为字段读取，且普通 own-data IC 精确命中，直接读取当前字段值。参数或局部变量槽继续拥有 receiver，从而省去临时 receiver 的一对 Dup/Free，并跳过一次字段 dispatch。失配仍回到原路径。

独立诊断中，d03/d04 微测试均有999次融合；未修改 Richards 的 N=1024 整进程诊断均有142849974次融合，数值控制为0。正式 d03 的 `get_arg0` 入口在0x2472a可见 `cmpb $0xf4,(%r12)`，s001对应入口直接完成原加载。这里确认了真实的成功路径与额外检查。二者各自的耗时贡献、代码布局贡献仍为 UNKNOWN。

副槽/共享动作确实能在微测试容纳4种shape，原型版本缓存也实测安装、命中3次并在getter重定义后失效。它们的单次整体得分尚无改善信号；不能据此推断这些设计在所有实现或程序中均无价值。详见 `mechanism_notes.md`、`walkthrough.md`。
