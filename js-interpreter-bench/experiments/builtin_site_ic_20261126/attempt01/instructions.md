# Acorn：高覆盖为什么没形成耗时收益

单独使用 Callgrind，只在解析的 Run 区间计数。复用实际 Release 的 quickjs.o；仅替换 qjs 启动器加入开始/停止采集的两个客户端请求。原始输出在 callgrind01/。Callgrind 的耗时不进入任何性能表。

|Run 指令分类|BODY|SITE|
|---|---|---|
|正则匹配器自身|93.8442%|94.0296%|
|命名属性读取 handler 与其常规查找|0.9514%|0.9654%|
|全部调用入口自身|0.7636%|0.7098%|
|全部原生帧自身，不含函数体|0.1285%|0.0539%|
|charCodeAt 函数体及其被调用函数|0.0343%|0.0003%|

总 Run 指令：BODY 30,260,443,817，SITE 30,200,791,064，变化 -0.1971%。两版 lre_exec 的指令数完全相同：28,397,670,550。
读取分类由普通/读 IC handler 的自身指令，加上它们进入 JS_GetPropertyInternal 的调用边计算；不把所有 find_own_property 都归到读取，因为构造/写入也使用它。调用入口列包含所有 JS/C 调用的入口工作；原生帧列包含所有 C builtin 的建帧/分派自身工作，不仅是 charCodeAt。函数体列含它调用的转换/学习辅助函数。剩下的解释器分派、解析、分配等工作没有硬塞进这几列。
Callgrind 的递归函数名 JS_CallInternal'2 等已合并；使用文件尾 totals 并与所有函数自身 Ir 之和核对，避免只看 summary:0 的客户端请求文件头。
SITE 真正减少了 charCodeAt 调用工作，但这块只占整段指令的一小部分；Acorn 仍有约 93.8% 指令在正则匹配器。属性读取约 0.95%，未成为整个负载的主导。本轮不把这些指令百分比当成耗时百分比，也不据此追加字符串原型读 IC。
