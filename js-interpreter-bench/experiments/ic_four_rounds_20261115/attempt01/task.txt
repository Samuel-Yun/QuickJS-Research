QuickJS：四轮 IC 突破实验
使用方法：把整份发给 coding 工具，它会顺序执行四轮。想分开投喂时，每次复制「通用任务」和对应轮次。
通用任务：固定 C，按四轮顺序实现和测量
目标：在 QuickJS-Research 里实现四个独立的、绑定到具体字节码位点的 IC 原型，看看一次命中能否减少更多实际工作，进一步缩小与 V8 --jitless 的耗时差距。直接诊断、写代码、编译和跑数据。不要只产出计划，也不要等我选模板。
底座和范围
- 每轮都从同一份冻结 C（TRANSITION_EDGE_STRONG） 派生。C 保留 EVAL_COLD 的属性 IC 和自身的 shape 转换缓存；不要带入 3B，也不要自动叠加前一轮赢家。
- C 源码包：`js-interpreter-bench/experiments/execution_paths_20261114/attempt01/candidates/TRANSITION_EDGE_STRONG-source.tar.gz`。核对同目录 manifest，用独立目录构建。候选共用同一默认 Release 构建方式；不加 LTO/PGO 来救分数。
- 建 js-interpreter-bench/experiments/ic_four_rounds_20261115/，轮次目录用 01_group_load、`02_call_recipe`、`03_constructor_plan`、`04_index_consume`。如果目录已存在，新开 attempt。保留旧实验、既有 Git 分支和用户改动；不自动 push。
- 不引入 JS JIT，不生成运行时机器码。不改 benchmark、输入、工作量或结果校验；不按基准名、文件名、JS 函数名或特定输入挑快路。示例仅用来讲机制，实际模板从真实字节码和动态覆盖中挑。
- 候选记录必须绑定到实际静态入口，例如函数字节码身份 + PC 或等价站点。一个全局帮助函数、写死某个内置函数名或纯静态融合对照，不能直接当作 IC 收益。
- 优先复用已有准备扫描和旁表；先只支持一种有覆盖的模板。没有命中的普通路径尽量不做新检查。预算放在快路本身，不另建一套大框架。
四轮怎么跑
1. 每轮先看覆盖，再做一个窄实现。 使用独立诊断版，沿用原 Run 区间：从目标负载找真实字节码、位点、进入次数和可特化比例。优先挑多个负载共同出现的模板，不以无关的固定计数门槛决定是否开工。选不到第一候选时允许换成该轮同类的一种；还是没有真实覆盖，记录证据并继续下一轮，别用人工微基准冒充全集覆盖。
2. 先证明少做了哪件事。 只做与本轮语义直接相关的差分和几个边界用例，再跑一组针对性父版/候选微基准，确认真的进入新路径。计数构建与 Release 计时分开。改字节码表示时验证保存、加载与合法入口；改帧、值或对象所有权时加定向 ASan/UBSan。保持正常失配和错误行为；不要用与本轮无关的重检查挡住实验。
3. 性能跑全集。 能运行的 Release 候选都先跑完整 Octane 17 项、SunSpider 26 项，每项 1 个独立新进程，沿用冻结案例脚本、N、CPU、时区和计时边界。Octane 报 14 suite 分层等权 GM；SunSpider 报 26 项等权 GM 和逐项耗时之和。负数表示耗时下降。参考 native_confirmation_20261108/attempt02 的协议与 A/EVAL_COLD/V8_ON 数据，以及 execution_paths_20261114/attempt01 的 C 数据。按当前安排，不为 C 单独开正式复测，不替每个候选自动加轮。 候选全集相对 C 若用旧数据，标为新旧单轮跨批次筛选；旧 A/V8_ON 是参考，不能把微小差异宣称为稳定收益。
4. 每轮完成就先汇报，再继续下一轮。 写出 results.md、相对 C 的补丁、原始计时及计数、逐项表和复现命令。对话里先给一条阶段结果：实现了什么、实际省了什么、两个全集各变多少、哪些项目主要变快或变慢。即使某轮没跑快，也保留结果并继续；确有阻碍就记录做到哪一步，独立轮次照跑。全部结束给一张四轮总表，不自动组合、覆盖底座或追加复测。
每轮 results.md 固定回答四件事：
项目	要报告什么
实际覆盖	真实负载的站点和命中次数，分清尝试、成功、回退
真的省掉什么	例如少做的 shape 比较、建帧、shape 搜索、分配、分派；次数不等同于时间
最终耗时	相对 C 的 Octane/SunSpider 完整逐项与整体；另列相对原版 A 的累计变化
结论	保留候选 / 无明显收益 / 没有覆盖 / 未完成；写明最重要的一条证据


第 1 轮 · GROUP_LOAD_IC：同一个对象，一次布局检查读多个字段
要验证：两个属性访问本来都能命中时，共用一次对象类型检查、shape 校验和属性数组寻址，能不能让真实负载更快？
1. 先在 RayTrace、DeltaBlue、Richards 与 SunSpider access-nbody 中查动态执行的直线片段，然后看全集覆盖。寻找同一局部或参数槽的两次自有字段读取，例如 o.x * o.y；两次读取之间不能有调用、写入或可重入操作。记录两次都满足普通自有数据字段的次数。区别于旧 CHAIN2 的 o.a.b：这里使用同一个 receiver、两个不同字段。
2. 在组选中的入口保存 {receiver_shape, offset_1, offset_2}，沿用已有可证明稳定的 shape 所有权/写时复制保护。命中时取当前 prop 一次，按原顺序读出两个当前值，保留两份结果分别需要的所有权；把后续操作需要的值按原栈效果交回去。首版不融合后续算术，目的是单独量一次检查服务两个读取。只命中一个字段时也继续走原序列。不得把读到的值存成缓存结果。
3. 只处理同基本块且可正确保留或排除中间跳转入口的形态。用字段更新、删除/重定义、getter 和不同布局的例子比对原 C；保存/加载如果涉及新指令就一起测。报告实际跳过的对象与 shape 检查、分派次数，以及每组额外记录字节数。给一个真实负载里的字节码前后示例。
第 2 轮 · CALL_RECIPE_IC：调用点缓存短函数模板，命中时不建 JS 帧
要验证：相比旧 C1 只省一次分派，能不能在一个真实热调用点省掉被调函数的整个解释器入口、栈帧和返回？
1. 从 Richards、DeltaBlue、Boyer、RayTrace 及一个 SunSpider 调用负载抽取真实调用目标和字节码。统计普通同步函数上的稳定目标。首版从 return this.x 或 return arg0 + 整数常量 中选一个动态覆盖最高的形态；如果没有覆盖，再从真实数据挑一个同等规模、无用户副作用的整数或自有字段模板。
2. 在一个普通调用 opcode 的具体 PC 缓存已验证的实际 callee 身份（或能等价证明的字节码及环境身份）+ 模板参数，确保目标身份及缓存持有关系存活。沿用原方法查找和实参求值；在原调用位置验证栈上已经解析出的 callee，不根据属性名猜目标，不在参数求值后重新读方法。命中后用预编译 C handler 完成该短函数。字段模板只读普通自有数据，整数模板只处理能准确复现原运算的值。守卫失败在执行模板之前进入原调用。
3. 只支持语义和入口条件可证明一致的普通同步函数和普通调用；先不做 tail call、构造、生成器、async、Proxy、bound 和需要通用 this 转换的形态。遵守现有栈限制和中断检查，在可能触发需要观察被调帧的中断或其他钩子时走原调用。测试同站点换函数、参数求值中换方法、异常和接收者变化，保持返回值与所有权一致。
4. 交付实际少进入多少次 JS_CallInternal、少建多少个帧；与相同目标的通用调用路径比较。只跳过一次分派或增添了一个函数名判断，不算此轮做到目标。
第 3 轮 · CONSTRUCTOR_PLAN_IC：构造点记住整段字段初始化
要验证：C 已经缓存单步 shape 转换，在稳定构造点直接采用最终布局，是否还能省掉中间转换和属性存储扩容？
1. 查 RayTrace、Splay、DeltaBlue、Richards 或 SunSpider access-binary-trees 的真实构造函数字节码与调用次数，选一种普通同步构造形态：若干 this.field = arg（或可证明等价的简单初始化），无 this 逃逸、无用户调用、按原规则返回接收者。先从一个合格的直线模板开始，依据结构识别，不能专门认 Vector 或某个函数名。
2. 在 new 对应的静态构造调用点学习 {原构造目标, new.target/实例原型约束, 初始/最终 shape, 参数到属性槽的映射}。利用原慢路径的实际创建/写入规则确认每一步都是新增普通 own 字段，并让缓存持有的最终布局可安全复用。首版优先做到：命中时一次分配最终需要的属性容量，按原源序初始化数据，去掉中间 shape 查找/切换和多次扩容。保留 C 的全局转换边缓存用于原回退路径。
3. 守卫须覆盖构造目标、原型、新增字段条件，尤其是原型上后来出现的 setter 或不可写数据属性。不要额外执行可能可观察的 new.target.prototype 读取；仅当本来就是可证明无副作用的原路径时快速处理。第一次写入前完成所有必要校验；分配失败沿原异常语义处理，不在已执行可观察步骤后重跑构造。测试方法/构造器替换、原型被改、setter、自定义返回对象及连续创建后释放。保留值与 shape 的所有权。
4. 分开计数：整段计划命中、少做的转换搜索、少做的 shape 切换、少做的属性数组分配/扩容。用 C 已经实现的单步缓存作为对照；只省查找就如实写，不能算成少分配。额外记录计划内存和保活成本。
第 4 轮 · INDEX_CONSUME_IC：读取数组元素后直接算并写回局部槽
要验证：QuickJS 已有整数索引快路时，是否还能靠“读取与消费一起特化”省掉类型分派、中间值和栈搬运？
1. 从 SunSpider 的 access-*、`math-、crypto-` 和 Octane 的 Gameboy、NavierStokes、Crypto 中找 get_array_el 及后续真实消费字节码。以热度和跨项目覆盖选一个：普通密集数组或一种 TypedArray，加一种整数局部累加/位运算；不预设具体类型一定有覆盖。不能匹配整个手写循环模板，也不改当前数组公共读取函数来冒充融合。
2. 在入口静态位点记录常见接收者类型、值/索引类别与消费模板。命中后按原边界和类型语义读当前元素，在同一个 handler 走原等价数值运算，再写回原局部槽，跳过被融合的字节码分派和中间值。先限定 int32 的可证明等价子集，溢出或其它 case 回原序列；不要用 C 的有符号溢出替代 JS 算术。
3. 不在 IC 中长期缓存数据地址、数组长度或已取元素。读取当前缓冲区或元素存储，用原来的长度、有效性与类型判断。空洞、负下标、越界、被 detach 或 resize 的 TypedArray、不支持的数组形态都走原路径；失配时不提前写回，保持原求值和异常顺序。测试上述边界及浮点、字符串、BigInt 回退。给出一处真实字节码前后对照，记录命中时究竟省下多少次派发、栈操作和中间值构造。
