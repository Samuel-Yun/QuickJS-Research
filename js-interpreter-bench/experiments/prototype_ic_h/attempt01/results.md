# 结果：H 有真实覆盖，但本批没有支持 Richards 净加速

本轮完成了受限 H 的实现、正确性/生命周期检查和同批 A/M/H 的450个
正式新进程，全部有效、30个完整15进程块，无缺失、重试或删除。
**不建议把这版 H 作为已成功的 Richards 优化推进。** 准入和命中确实
成立，普通查找减少了，但原型小例子及原 Richards 都没有得到方向明确
的净收益；两项控制还出现了相对 M 的探索性退化信号。

## 实际覆盖与机制

独立 M 准入观察中，原 Richards schedule PC30、PC83 和 TCB.run PC73
每 Run 的10671/6573/6573次读取均满足普通对象、直接一层 data、两边
hashed 条件，N2对应翻倍。原型小例子4096次也全部合格。这补齐了
上一轮 UNKNOWN，不是从 V8 Map 或旧 inherited 分类推测。

H 在单槽里增加 holder_shape，不缓存属性值或函数。命中先匹配
receiver shape，再检查当前直接 holder 的 shape，读当前 prop 槽；
miss 保留原查找。get_field/get_field2 的接收者/栈语义、原方法及尾调用
未改。正式源码只改四文件；补丁和制品身份见 H_manifest.json。

本轮 H 诊断 N1 显示：前两目标分别命中10670和6572次，各只剩2次
普通 own 探查；第三处6573查询中3023命中、3550回退，普通探查7100次。
四类 task 单槽仍有替换。H 也覆盖其他合格读点，不只这三个位置。
这些是次数，不是各位置 self-time，不能由此算出应节省多少毫秒。

## 同批正式时间

单位为 **ms/完整 Run**。两种方法案例每 Run 含4096轮，Richards 是
原始完整 Run。所有三版同脚本、输入、共同N、可靠内部单调时钟；
首次 Run 计入，无计时前 workload 预跑。微例预建对象和所需 Setup
在计时外；Richards Run 内原有对象创建、断言、GC/helper 仍在内。

## 正确性、维护和内存代价

96/96严格/非严格语义进程通过，声明位置及this独立断言已验证。
正式驱动30/30个N1/N2正确性及15个选定N检查也通过。H通过有限
上游测试、GC循环、192个OOM编译限额、ASan/UBSan、热bytecode
跨A/M/H copy/ROM加载和嵌入。内部检查证明修改前继承已命中，
未hashed状态拒绝填充，重载为空后重新填充；另有32次large-shape
COW分配失败保留旧缓存和值。测试开发中的失败/修正均原样保留，
没有用缺陷版本计时；这些不是完整test262或所有语义的证明。

实测site从16B到24B，所有own site也多8B。Richards创建311个site，
请求数组4976→7464B；M与H的N1 shape边retain/release分别106/106、
7274/7274，H的N2为14374/14374。诊断结束数组活跃字节归零。
数组空间、额外间接保活和RSS是三种口径；后两者的峰值字节未测。

## 能解释什么，还缺什么

已经排除“这些位置根本不能准入”和“H没有命中”这两个问题，但减少
查找没有自动形成可确认净收益。holder守卫、替换引用维护、eager数组
膨胀、native布局及宿主波动都可能影响总时间，目前不能分项归因。
尤其无目标字段读取的numeric_control相对M也偏慢，不能把整个变化
都说成每次属性读取新增检查的成本；它提示非目标变化仍未隔离。

本批只有一台未锁定功耗/频率、Windows后台未知的WSL2主机，波动和
较宽区间限制判断。没有根据结果删异常值、调N或追加样本。H的
single-slot替换也不是V8 handler或通用原型失效系统，未运行V8。

下一步若继续，只能另开任务先复核非目标控制及native布局/环境影响，
再判断是否值得保留该受限方案；本轮不加命中路径、PIC或退出策略来
追求正结果。当前结论是：**覆盖与语义检查成立；Richards净收益未获
支持，且有控制项退化信号。这版H不作为已验证优化合入。**
