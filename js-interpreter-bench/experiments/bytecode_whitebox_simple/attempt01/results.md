# 小程序实验小结

## 做了什么

在同一 WSL2 Ubuntu/x86_64 环境中，使用冻结的 QuickJS 2026-06-04 与 d8 15.6.21（`--max-opt=0 --no-lazy`），实际完成运算表达式、数值循环、条件分支、普通调用、own 属性读取、原型方法调用六类程序。每类源码和输入完全相同，未移出方法读取，未改正式 VM；独立诊断构建只用于打印和计数。六类各以 N=1、2、64 做独立正确性检查，36/36 通过，并导出六个主函数及两个被调用函数的真实字节码。原始输出与解释分开保存。

数值循环、own 属性、原型方法各采集两引擎×30个新进程，共180/180有效样本。已有单调时钟在 process 内包围 N 次目标调用；对象建立、静态编译、启动均在外，首次调用在内，无预热。共同 N 由双方内部时间校准，正式样本偏短也保留。`summary.csv` 给出完整统计，下表单位是一次完整目标调用的微秒，包含4096次内部循环及摊薄 driver，不是单条操作成本。

独立审计核对了全部原始输出、退出码、源码和制品哈希、实际命令、选定工作量及统计公式。每个案例两种先后顺序各十五轮，各组均为三十条；全部正式样本在同一次系统启动中完成，旧文件保持不变。选定工作量还有六次独立正确性复核。

| 案例 | QJS median [Q1,Q3] µs | V8 median [Q1,Q3] µs | V8/QJS |
|---|---:|---:|---:|
| 数值循环 | 43.782 [42.426,47.153] | 54.839 [51.301,60.431] | 1.253 |
| own 属性 | 70.959 [68.035,74.366] | 62.875 [59.863,64.295] | 0.886 |

## 实际看到什么

三个案例没有统一的快慢方向。数值循环 QJS 的最终字节码为14条/18字节，V8为17条/32字节；QJS 的 `add_loc` 直接更新局部 sum，`inc_loc` 更新 i。V8 则出现 Ldar、Add、Mov、Star 和 Inc 等组合。实际 d8 的 Ldar/Mov handler 反汇编还确认：这里的虚拟寄存器通过帧内存槽读取、写回，不等于 CPU 物理寄存器。

own 属性的主函数两边均为17条静态指令，结果却偏向 V8。独立 QJS 计数构建中，4096次 value 读取全部自身数据属性命中，没有进入通用属性 helper；这不表示读取免费，源码内仍有 shape 哈希查找、类型检查与对象引用管理。不能把 helper 为零解释为没有属性访问成本。

原型案例两边主函数均19条；QJS 的 `get_field2 step` 保留 receiver，随后 `call_method`，V8 分成 GetNamedProperty 与 CallProperty1。QJS 诊断实际记录4096次一层原型命中、4096次方法进入，callee 中另有4096次自身 bias 命中。callee 的静态序列为 QJS 7条、V8 3条；但这不能把总体时间差按指令数换算。

## 目前能解释到哪一步

能够逐组指出值如何流动、哪些是循环支撑、哪里读取属性、哪里准备 receiver、哪里调用和返回；还能确认 QJS 本次诊断的属性快路径。d8 的九个实际 handler 已用 code-event、活进程映射和 ELF 反汇编定位；可见搬运、检查、辅助调用及分发代码。它们证明制品含有这些路径，不证明正式样本内部每条分支的命中率。

为了核对诊断版本，另将六份相同源码交给正式构建目录与诊断目录的编译工具序列化，得到的字节完全一致。这个检查加强了字节码对应关系，但不是直接读取正式进程内存，也不把诊断构建的耗时作为正式证据。

## 还缺什么证据

以上都是点估计，没有统计显著性检验或指令级时间分解。V8 精确源码/构建参数与 IC 命中率 UNKNOWN，官方单文件源码获取失败已保存。QJS 诊断不是正式 binary，不能使用其耗时；没有完整动态 opcode profiler。逻辑指令执行次数只能按控制流推导，也不等于实际 native dispatch 次数。WSL 宿主功耗、频率与后台任务未完全控制。

六十六个正式样本低于校准的一秒门槛，最短约零点六二秒，全部保留。这说明一次校准不能保证后续时长稳定。首次调用的反馈建立、运行期状态变化和可能的垃圾回收也计入，因此不能将指标改称纯解释器循环时间。

## 下一步做什么

先与导师确认应优先补“原程序热点路径频率”还是“调用/属性成本的采样分解”。原型案例只提示回到原 Richards 的 `Scheduler.prototype.schedule` 中 `currentTcb.run()` 与 `TaskControlBlock.prototype.run` 中 `this.task.run(packet)` 核对 receiver、原型深度及调用链。这里是单一稳定 receiver，而 Richards 的 task 类型不同；目前不能声称解释了 Richards 总体差距，也不能恢复手工缓存方法 A/B 的优化收益结论。
