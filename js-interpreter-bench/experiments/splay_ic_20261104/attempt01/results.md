# Splay IC 跟进：有新的 Run 内证据，但本轮尚未完成

**状态：BLOCKED_ENVIRONMENT_PARTIAL。正式性能样本为 0，不交付 OPT 性能结论。**

## 做了什么，完成多少

从干净 myx / `894e0a35ff331d4235370dc26112e5916c27c567` 开始，核验并复用冻结 A、M、官方 d8，未改正式 binary、旧源码或旧数据。独立 QuickJS 诊断副本沿用既有 opcode scope，新增 load/compile、Setup、Run、校验、TearDown、销毁阶段；嵌套 JS frame 清除调用者属性上下文，返回时恢复。PC 在 opcode 参数解码前记录，不把 `sf->cur_pc` 直接当当前 opcode。

初版密集诊断 41 条另存。新稀疏版本实际保存 **44/68** 个有效独立进程：前10个 Run 单元的 A/M×repetitions=1/2 完整；PdfJS 保存 A.N1、M.N1、A.N2；Mandreel 保存 A.N1。其余24个位置缺失，见 `summary_v2/coverage.csv`。两系列不合并成85条完成数。已保存记录的归档 SHA、查询分解、更新分解、真实 opcode 起点及 benchmark 自带门禁均通过离线检查；这不代表缺失部分通过。

固定 d8 的 Splay N1/N2 实际字节码、IC/Map 日志及 Run 前后 DebugPrint 输出已保存。该 release 的 DebugPrint 只打印函数身份，**未取得反馈槽快照**；初版 `v8/status.json` 措辞由 `v8/status_v2.json` 更正，原文件和原输出保留。

## 实际看到什么

下表全部为新稀疏诊断的 **Run 阶段、repetitions=2 合计**，不是时间；`find` 是原逻辑查找进入次数，不是 native call 数。

|项目|A 普通读取|M 查询|M 命中|M 回退|A/M 的 find|M 更新|M 替换|
|---|---:|---:|---:|---:|---:|---:|---:|
|Richards|403742|403742|322726|81016|484672 / 161946|86|0|
|Splay|45664|45664|23001|22663|48864 / 25863|18343|18324|

两个项目中，`A find − M find` 恰与命中数相同：本次已对齐范围确实观察到命中省掉普通查找。但 Splay 同时进行18324次不同 shape 的缓存替换；Richards Run 内没有替换。这是比旧全进程数字更具体的差别，仍不是维护成本抵消收益的时间证明。

Splay 的 Setup 本身有1342328次读取、565543次替换，远高于这两个 Run 内的次数。TearDown 另有11975次替换。旧全进程计数不能直接命名为 Run 开销。必需 Setup 会调用树操作并准备缓存；“无额外 workload 预跑”不等于所有字段全冷。

`splay_` 的前三替换读点如下，按替换频率选择，不称耗时热点：

|QJS PC / 属性|查询|命中|回退=普通 find|替换|缓存 shape retain/release|

三个位置的回退均进入合格 own 数据属性更新，未记录 descriptor、继承、exotic 或通用 helper 回退。PC43 的每次实际普通查找只有一次桶读和一次链候选比较。M 的 probe/find 在冻结机器码窗口中是内联工作，不能用“每次调用一个昂贵 C 函数”解释退化。尚未完成接收对象 shape 种类、完整布局及转换序列采集，不能说只是无关字段变化，或凭相同 offset 放宽守卫。

## V8 对应证据

同份 Splay 源码的两个 `current.key` 表达式，在实际 Ignition dump 中分别为 PC41、PC118，**共享 FBV[12]**；`current.right` 的对应条件读取为 PC127 / FBV[26]。不能拿这些数字和 QJS PC 直接对齐。实际日志有对应 key 位置的0→1、1→P转换，支持已经形成多态反馈；日志覆盖加载和 Setup，不是 Run 内查询数、成功快路径次数或命中率。两项计数及直接槽快照均 UNKNOWN。参考源码为 `37fb84941c9be9f9914ee50b1ad366f06a1bd764`，实际 d8 构建 commit 仍 UNKNOWN；未重建/替换 V8。

## 目前能解释到哪一步

支持一个待检验解释：Splay 在省掉部分短查找的同时，仍频繁支付失配后的普通查找与 shape 边维护；Richards 的大量稳定 own 读取则很少更新。**没有本轮受控时间证据证明哪项成本占主导，不能把总差距归给维护，也不能计算单次 miss 成本。**

准备了“计时前把三个指定读点恢复普通读取”的独立机制控制源码，计划同 ELF ON/OFF 加原 M 桥接和数值控制。该控制尚未构建、通过门禁或采样，不能把它当实验结果。没有据此选择/实现 OPT，U 未参与。

多次 WSL 会话消失/boot 改变，部分构建/诊断未留下正常退出记录；一份新诊断 A 实际变成0字节。前台恢复通过了新 A 的烟雾检查，但后续在 PdfJS、Mandreel 的待保存 M 位置再次中断。**原因 UNKNOWN，不声称是 OOM，也不将其报告为 benchmark 正确性回归。** 结束前冻结 A/M/d8、13项源文件及两项依赖复核仍一致，极小 smoke 通过（`post_artifact_probe.json`）。
