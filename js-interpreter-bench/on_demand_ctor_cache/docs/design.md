# 设计说明

## 先理解它省的是什么

例如一个构造器只做这件事：

```js
function Pair(x, y) {
    this.x = x;
    this.y = y;
}
var p = new Pair(3, 4);
```

原版 A 每次执行 `new`，都会进入构造调用、运行构造器字节码，逐个写入字段。构造计划把“字段 x 来自第 0 个实参，字段 y 来自第 1 个实参，结果使用这个 shape”记在这个 `new` 访问点上。再次遇到同一个构造目标且检查通过，就直接创建最终布局的对象，把实参填进属性槽。

它仍然创建对象和属性数组。省掉的是普通构造调用入口、构造器解释帧、逐条解释字段赋值以及逐次新增字段的工作。没有生成机器码。

## 本轮增加的两件事

父版 R3 给每个构造位点预留完整的 96 字节记录。本方法把它拆成小记录 `FourSite` 和完整计划 `FullPlan`：

| 位点状态 | 当前 x86-64 Release 记录占用 | 做什么 |
|---|---:|---|
| 还没有完整计划 | 32 B | 保存位点位置、实参数量、计划指针、负缓存目标 |
| 已学会完整计划 | 32 + 96 = 128 B | 另分配计划，保存构造目标、shape、字段到参数的映射 |

没有学到计划的位点比 R3 少 64 B。已经学到的位点反而多 32 B，命中时也多读一次计划指针。这些是记录请求字节，不等于整个进程 RSS；另有分配器开销。

第二件事是负缓存。某个构造目标的字节码确定不符合模板时，记住它的身份。下次仍是它，就不再解析模板，继续执行普通构造。负命中省的是判型，普通构造、字段写入和对象分配都还在。

## 一个 new 位点怎样执行

对应 `quickjs.c:18329` 的 `OP_four_ctor`：

```text
取出该 new 位点的小记录
  │
  ├─ 有计划，目标/原型/写入条件等检查通过
  │     → 用最终 shape 分配对象
  │     → 按计划把实参复制进属性槽
  │     → 清理原调用操作数，压入结果
  │
  └─ 没有命中
        ├─ 当前目标等于负缓存目标 → 跳过模板解析
        └─ 否则 → 检查能否学习
              ↓
        执行原来的 JS_CallConstructorInternal
              ↓
        成功且符合条件 → 观察真实结果，建立/更新正计划
        成功但不符合   → 只在目标确定不支持时记负缓存
        抛异常         → 原异常路径
```

学习发生在普通构造成功之后，使用实际构造结果确认最终布局；不会为了学习再执行一次构造器。

## 支持的构造模板

`four_runtime.inc:30` 的 `plan_recipe` 检查最终字节码：

```text
push_this
put_loc0
重复 1～8 次：get_loc0 → get_argN → put_field atom
return_undef
```

只接受简单参数直接写到不同字段的普通同步构造器。加法、调用、闭包引用、不同返回方式等不符合这个模板。判断依据是函数类别、字节码和描述符，没有按基准名、构造器名或字段名启用。

## 命中仍然检查什么

- `plan_try`：当前 callee 必须等于记录中的构造目标。
- `plan_base`：callee 与 new.target 一致，函数类别、构造资格、实参数量、栈与 GC 条件符合要求。安装中断处理器时回普通路径。
- `plan_proto`：当前函数的 prototype 仍是普通自有数据属性，值是符合要求的普通对象。
- `plan_chain`：每个待初始化字段的当前原型链上没有会改变赋值行为的访问器或只读属性；链上对象类型和深度也符合要求。
- 分配前保留两次已有的中断轮询；分配失败不会重新普通构造、重放用户代码。

原型链资格检查在每次正命中时仍然执行，本版本没有叠加后续的原型票据。对象分配方式也沿用 R3。

## 哪些失败会记住

实现位于 `sparse_runtime.inc:22`：先排除冷函数；准备好的 JS 函数字节码符合模板时不记负缓存，其余确定不支持的目标类别/模板可以记住。负缓存以对象身份比较并持有强引用。

参数不够、原型状态、空 shape 找不到、GC 预算等暂时条件不直接作为负缓存结论。目标变了会重新尝试。当前实现可以同时保留原正计划和另一个不支持目标的负记录；新正计划成功发布时清除负记录。

## 引用和释放

`FourSite.negative`、`FullPlan.callee` 持有 JSValue 强引用，计划持有 initial/final shape 引用。替换时先发布新记录，再释放旧引用；释放函数字节码时一起释放。`quickjs.c:6708` 把这些引用接入 GC 标记，`:36529` 接入释放。

完整计划用可选的 `js_mallocz_rt` 分配。分配不到只是不启用计划，已经成功的普通构造结果继续返回。没有改成必须分配缓存才能完成 JS 构造。

## 从 A 带过来的其它执行路径

完整补丁还包含以下已有实现，这解释了为什么属性读取微基准也能体现收益：

| 路径 | 主要实现 | 命中省掉什么 |
|---|---|---|
| 属性读取 IC | `read_ic_opcodes.inc`、`read_ic_runtime.inc` | 普通对象的 shape 相同，直接按缓存 offset 读当前槽值，省属性哈希查找 |
| 读取融合 | `V6_PREPARED_BORROW` | 已准备的局部/参数读取与字段读取融合，省一个字段读取 dispatch 和临时 receiver 引用/栈操作 |
| 读取记录用于写入 | `OP_put_field_shared` | 在相同 shape、普通自有可写数据字段条件下复用 offset，省写入路径的再次查找 |
| 冷函数准备 | `js_cold_entry_call`、`rdi_prepare` | 对部分 eval 产生的普通函数延后到首次调用才准备 IC；准备后恢复普通函数入口 |
| shape 转换缓存 | `edge_strong_helpers.inc` | 已决定新增属性后，缓存原 shape、atom、完整 flags 到目标 shape 的转换，省全局 shape 搜索 |

属性读取的直接原型快路仍只覆盖代码中允许的普通对象；没有带入后续 RegExp 类别扩展。shape 转换缓存是运行时 32 项，保留原属性扩容和初始化过程。

## 字节码如何接起来

`rdi_prepare` 在最终字节码上为读点和构造点预留稳定旁表。`four_prepare` 把 `call_constructor argc` 换成同长度的 `four_ctor record_index`，原 argc 放在小记录里。因此指令偏移和分支入口不因这次替换移动。

保存时 `JS_WriteFunctionBytecode` 将这些运行时 opcode 还原成普通形式，记录中的 argc、atom 写回序列化内容；加载后重新准备旁表，不把进程内指针写进字节码文件。ROM 输入也拥有可写的执行副本。本包的 `tests/serialization.c` 会先执行，再保存，并分别用普通模式和 ROM 模式加载执行。
