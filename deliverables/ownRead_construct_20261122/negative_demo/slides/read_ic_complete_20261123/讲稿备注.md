第 1 页

这次直接用仓库的 bytecode_demo.js，construct 先负责生成对象，今天先看 ownRead。对象的 x 是 3、y 是 4，所以每轮加七，循环结束输出 sum=700。两版 ownRead 的指令区都是七字节，IC 编号、到记录的字节距离和属性槽号是三件不同的事。

第 2 页

第一条 get_arg0 给 obj 增加临时引用并压栈，此时栈上还是对象。get_field 调用 GET_FIELD_INLINE，keep 和 is_length 都是零，所以按 x 的 atom 查找，最后走替换栈顶的分支。find_own_property 找到普通数据属性后取出 3，再释放临时 obj 引用，把栈顶换成 3。这里把宏的所有分支都放出来了，原型、特殊对象和异常分支也保留，按左列再右列看。

第 3 页

这页把冻结版的整个融合宏都放出来，所有守卫、命中体和最后的回退都在。命中时只把属性值 3 压栈，没有先压 obj，所以省掉临时对象引用的增减。进入这个 handler 后 pc 在一，get_field_rdi 占五字节，加五就到六的 return，字节码表中那条读取指令仍在，只是这次不执行。缓存为空或布局不符时会落到最后一行，把 obj 压栈，交给下一条 get_field_rdi。

第 4 页

前一页的融合入口失配时先把 obj 压栈，这里才开始执行普通的读 IC 指令，它自己仍会探测一次缓存。此时 get_field_rdi 的 opcode 已经读过，pc 在二，读出 delta 六后从二加六找到记录，再把 pc 加四推进到六。本例 keep 为零，表示最后把对象替换成属性值，代码里的直接原型分支仍完整放出，但 keep 为零时不会进入它。布局匹配就按槽号读值并跳到共同收尾，失配才继续下一页的正常查找。

第 5 页

失配后从记录里取回 atom，像 A 一样查自有属性和原型链，特殊属性及对象则进入通用读取路径。普通自有数据字段满足条件时更新 shape 和槽号，直接原型缓存所需的条件及其他回退也都保留在代码里。命中和失配最后都到 name 拼出来的 done 标签，本例 keep 为零，释放临时 obj 引用并用属性值替换栈顶。这两页连起来就是冻结版 read_ic_opcodes.inc 的完整内容，没有删分支或用省略号代替代码，仅把宏行尾续行符去掉并换行排版。

第 6 页

左边先给出当前启用的单槽配置和记录结构，再完整展示 rdi_probe，shape 相同才返回槽号，失败用 UINT32_MAX，零本身是合法槽号。rdi_probe 的四槽条件编译分支也原样保留，但冻结版容量是一个槽，所以那个分支不启用。右边完整保留自有字段和直接原型记录的更新函数，包括 shape 引用的持有和释放，末尾仍由 return 取出栈顶的属性值。诊断计数宏在未插桩 Release 中为空操作，这里没有增加运行次数或性能结论。

第 7 页

沿用前四页的同一段例子，现在看 construct 里的 new，实际传入的参数是三和四。get_var 取出 Pair，dup 再复制一份作为 new.target，所以调用前是两个 Pair 加两个参数。两版 construct 都是十字节，只有偏移六的调用入口不同，record 零是记录编号，参数数量仍是二。Pair 自己的十七字节完全相同，命中时直接由 C 路径完成构造，失配仍可执行这份函数体。

第 8 页

左边是原版 A 的完整 new handler，它从字节码读出 argc，再把 callee、new.target 和参数交给普通构造入口。右边的 helper 用 new.target 的 prototype 创建 this；原型不是对象时，还会走原本的 realm 和默认原型处理。普通调用成功后，左边释放两个目标引用和实参，在栈上留下新对象。这一页先看对象从哪里来，下一页看 Pair 函数体怎样被调用。

第 9 页

这是原版 A 的完整普通构造分发函数，类型、中断、派生构造器和异常分支都保留了。Pair 走 legacy constructor 分支，先创建 this，再用 JS_CallInternal 执行 Pair 的字节码。Pair 内部依次写 x 和 y，最后返回 undefined，所以这个函数会把刚创建的 this 返回给 construct。A 本来也会复用 shape；后面的收益主要来自省掉解释构造器和逐次添加字段的工作。

第 10 页

冻结版先用两字节记录编号找到这个 new 位点，再从记录里拿到原来的参数个数。four_ctor_try 成功就使用新对象；失败仍执行原来的普通构造，不能跳过构造器应该产生的行为。普通构造成功且适合学习时，才用真实结果建立计划，否则可能记住明确不支持的目标来减少下次判型。异常处理和最后的值释放都保留，缓存计划也不会让每次 new 返回同一个对象。

第 11 页

这里检查实际字节码，不按函数名或属性名特判，Pair 恰好符合直接把实参写进不同字段的模板。识别结果记住字段的 atom 和参数下标，本例是 x 对参数零、y 对参数一。右边是冻结版的实际结构：new 位点的小记录指向可选的完整计划，完整计划保留目标、shape 和映射。空位点是三十二字节，真正学成后另分配九十六字节计划；这是当前 x86-64 Release 的大小。

第 12 页

学习前先做资格检查，随后仍然正常执行一次 Pair，再用实际返回对象确认原型、字段顺序、描述符和最终 shape。确认无误才按需分配完整计划，保存构造目标、initial、final 和参数映射；代码也保留旧引用的释放。冻结版前后都要求能找到同原型的空 shape，所以示例先创建 empty 并一直保留它。学习不需要再跑一遍 Pair，分配缓存失败也不会把已经成功的普通构造结果改成失败。

第 13 页

有计划并不等于随时能直接写槽，目标函数、new.target、参数数量和原型仍要符合要求。右边沿当前原型链检查相关字段，最近一层描述符决定能不能直接初始化，setter 或只读属性都会让它回退。左边还保留栈空间、中断和 GC 预算条件，可能触发可观察行为时继续走普通路径。所以命中有固定成本，不能把它描述成完全没有检查的裸写内存。

第 14 页

检查通过后，先按 final shape 创建一个新对象，再根据 recipe 把参数三和四复制到 x、y 对应的属性槽。这里没有进入 Pair 的解释器帧，也没有逐条执行 Pair 的 put_field；Pair 字节码仍保留供回退使用。对象和属性数组仍要分配，参数引用也仍要管理，不能把命中解释成省掉所有分配。分配失败会直接带着原异常退出，不再普通构造一次；这份快照只证明计划已学成，没有提供具体命中次数或耗时。

第 15 页

继续保留前面的 Pair 正计划例子，另外用 constructUnsupported 中独立的 new 位点反复调用 Unsupported。Unsupported 的参数后面还有加一，实际字节码里多了 push_1 和 add，不能匹配当前的直接赋值模板。两版都算出 negativeSum=400，冻结版快照显示这个位点没有正计划，但已经记住负目标。这里的快照只证明记录已建立，我们没有统计逐次命中数，也没有据此声称提速。

第 16 页

左边先用对象身份比较当前构造目标和保存的负目标，匹配就从资格入口返回零，普通构造仍会执行。首次不支持时，右边在普通构造成功后确认目标确实不符合模板，再持有它的引用并释放旧目标。后续右边的 sparse_remember 仍会进入，不过开头再次比较身份后就立即返回，冻结版还有这笔检查成本。它只记稳定的模板或类别不支持，冷函数和参数数量、原型、GC 等临时条件失败都不能直接当成不支持缓存。
